Betax 회계·세무 SaaS 참여 종료 (2026.02) 자사 개발
NARINER 자체 개발 · 2023.10 ~ 2026.02 · 3개 고객사 운영 · 백엔드 담당
Kafka 비동기 처리, Redis 캐싱, Kubernetes 오케스트레이션, Prometheus+Grafana 모니터링을 실 서비스에 적용한 회계·세무 웹 SaaS. 03 MSA 세금계산서 솔루션의 종단(SaaS 레이어)으로, SAP과는 03의 JCo Server·중계서버를 거쳐 연동된다.
Kafka비동기 처리
Redis캐싱 전략
K8s오케스트레이션
+
Kafka — 비동기 경계와 실패 격리
  • 선택 기준: 세금계산서 발행처럼 외부 처리 시간이 길고 동시 요청이 몰리는 업무를 동기 API 체인에서 분리해, 요청 스레드 점유와 연쇄 장애를 줄이는 비동기 경계로 Kafka 채택
  • 토픽 설계: journal-events, budget-alerts, tax-invoice-requests 등 업무 이벤트의 변경 주기·실패 영향 범위에 따라 7개 토픽으로 분리하고 Producer/Consumer 책임을 명확히 구분
  • 실패 전략: 일시 오류는 FixedBackOff로 제한 재시도하고, 재시도 한계를 넘은 이벤트는 DLT(Dead Letter Topic)로 격리해 정상 이벤트의 흐름을 보호
  • 운영 기준: Consumer Lag을 Prometheus·Grafana로 관찰해 단순 서버 정상 여부가 아니라 생산 속도와 소비 속도의 불균형을 장애 징후로 관리
  • 결과: 동기 처리 시 작업자 대기가 발생하던 발행 요청을 즉시 응답 구조로 전환하고, 완료 결과는 이벤트 흐름에서 후속 처리
Redis — 조회 모델과 일관성 경계
  • 자료구조: 환율·회사·거래처 마스터처럼 키로 조회하고 결과 전체를 함께 읽는 데이터는 Redis String 기반 Key-Value 캐시로 저장. 부분 필드 갱신용 Hash나 순위용 Sorted Set보다 조회 패턴에 맞는 단순 구조 선택
  • TTL 기준: 환율·분석키는 24시간, 회사·거래처 마스터는 12시간으로 변경 주기와 허용 가능한 데이터 신선도에 따라 만료 시간을 차등 설계
  • 일관성: DB를 원본 데이터(Source of Truth)로 유지하는 Cache-Aside 패턴을 적용하고, 변경 시 @CacheEvict로 무효화해 오래된 캐시 노출 구간을 통제
  • 장애 격리: Redis를 필수 저장소가 아닌 가속 계층으로 두고 CacheErrorHandler로 장애 시 DB fallback — 캐시 장애가 서비스 장애로 전파되지 않는 구조
  • 적용 범위: 반복 조회가 명확한 32개 메서드에만 @Cacheable / @CacheEvict를 적용하고 캐시 히트율을 관찰해 효과를 검증
인프라
  • Docker Compose 로컬 환경 → Kubernetes 운영 환경 (HPA, Rolling Update, Liveness/Readiness Probe)
  • Prometheus + Grafana 모니터링 대시보드 구축 (캐시 히트율, Kafka Consumer Lag 등)
  • Spring Actuator + Micrometer 기반 메트릭 수집
기술 스택
