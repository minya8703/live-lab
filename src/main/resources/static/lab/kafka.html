U5 · Kafka 처리량 라이브 데모

Kafka 메시지 처리 + DLT — t4g.small 안에서 다뤄봅니다

Kafka 3.7 KRaft 모드 · 3 파티션. Producer가 주문 이벤트를 발행하면 Consumer가 소비하고, 17의 배수 orderId는 의도적으로 실패시켜 FixedBackOff 500ms × 3회 재시도 → DLT 라우팅까지 흐름을 봅니다.

⚖ 이 데모의 trade-off (의식적 선택)

현재Spring Kafka 표준 — DefaultErrorHandler + FixedBackOff(500ms × 3) 의 레코드 단위 블로킹 재시도.

한계17의 배수 메시지가 걸리면 해당 파티션 컨슈머 스레드가 1.5초 stall → throughput 그래프가 계단식으로 낙하. 3 파티션 비대칭으로 성공 카운트는 spike, DLT 는 점진 증가하는 비대칭이 보입니다.

고처리량 운영급메인 토픽을 막지 않는 Non-blocking Retry Topic 패턴 — order.retry.500ms → order.retry.5s → order.DLT 의 단계 분리. Spring Kafka 의 @RetryableTopic 또는 RetryTopicConfigurer.

현 사이트가 안 가는 이유t4g.small 2GB 안에서 토픽 4 개 추가는 메모리 무리. 코드 변경 자체는 가능하나 별도 Unit (U12 후보) 으로 분리해 *개선 비교 회고* 로 노출 예정.

발행 후 약 500ms 간격으로 상태를 폴링합니다. 17의 배수인 orderId(약 5.9%)가 의도적 실패 → 재시도 → DLT로 흐릅니다.

아키텍처 결정 — Kafka를 왜, 어떻게 경계로 두는가

  • 선택 기준: 즉시 결과가 필요한 단순 조회·명령은 동기 API가 맞다. Kafka는 생산자와 소비자의 처리 시간을 분리하고, 순간 트래픽을 버퍼링하며, 이벤트 재처리가 필요한 업무에 사용한다.
  • 토픽 경계: 토픽은 서비스 이름이 아니라 이벤트의 의미·보존 기간·접근 권한·실패 영향 범위를 기준으로 나눈다. 서로 다른 변경 주기나 장애 정책을 가진 이벤트를 한 토픽에 섞지 않는다.
  • 파티션·순서: 이 데모는 orderId를 메시지 키로 보내 같은 주문의 이벤트가 같은 파티션에 배치되게 한다. 순서는 토픽 전체가 아닌 파티션 내부에서만 보장되며, 3개 파티션과 Consumer concurrency 3으로 순서 범위와 병렬 처리량을 맞췄다.
  • 전달·중복: acks=all과 record 단위 ack를 사용하지만 재시도 구조는 같은 이벤트를 다시 전달할 수 있다. 금융·주문 상태를 실제로 변경하는 Consumer라면 eventId 저장이나 업무 키의 유니크 제약으로 멱등성을 보장해야 한다.
  • 실패 격리: 일시 오류는 제한 횟수만 재시도하고, 지속 오류는 원본과 동일한 파티션 수의 DLT로 보낸다. DLT는 폐기함이 아니라 원인·헤더를 확인하고 수정 후 재처리하는 운영 큐다.
  • 내구성과 가용성: 현재 acks=all이어도 단일 브로커·복제 계수 1이라 브로커 장애까지 견디는 고가용성은 아니다. 운영 환경에서는 다중 브로커, replication factor 3, min.insync.replicas를 함께 설계해야 의미가 있다.
  • 관측 기준: 요청 수가 아니라 전송 시도·브로커 ACK·발행 실패를 분리하고, Consumer Lag·재시도율·DLT 유입량을 함께 봐야 병목이 Producer, Broker, Consumer 중 어디에 있는지 판단할 수 있다.

이 데모가 측정하는 것

  • Producer가 livelab.orders 토픽(3 파티션)으로 전송을 시도하고, KafkaTemplate.send() 완료 결과로 브로커 ACK와 발행 실패를 분리 집계. JsonSerializer + acks=all.
  • Consumer가 메시지를 소비. orderId % 17 == 0이면 IllegalStateException으로 실패 시뮬레이션.
  • 실패 시 DefaultErrorHandler + FixedBackOff(500ms, 3)가 재시도, 한계 초과 시 DeadLetterPublishingRecoverer가 livelab.orders.DLT로 라우팅.
  • DLT는 원본과 같은 3 파티션으로 구성해 실패 레코드의 원본 파티션을 유지. 현재 화면 카운트는 별도 DLT 컨슈머가 아니라 DeadLetterPublishingRecoverer 호출 시점에 기록.
  • UI는 500ms 간격으로 /api/kafka-demo/status를 폴링해 진행 상태 라이브 갱신.
