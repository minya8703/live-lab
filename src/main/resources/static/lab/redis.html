U4 · Redis 캐시 라이브 데모

Redis Cache-Aside — 조회 장애를 DB 경로로 격리하는 데모

Postgres 100,000건에 대해 카테고리별 집계 쿼리 (GROUP BY · 인덱스 의도적으로 미사용)를 캐시 없음 vs Redis 캐시로 같은 환경에서 실측합니다. Redis 조회 장애 시에는 CacheErrorHandler로 오류를 격리하고 DB 조회를 계속합니다.

⚖ 이 데모의 trade-off (의식적 선택)

현재읽기 전용 Cache-Aside 데모. GenericJackson2JsonRedisSerializer + 단일 Redis 인스턴스 + TTL 60초.

자원 보호연결 peer 기준 벤치마크는 분당 누적 400회, 전체 캐시 초기화는 분당 10회로 제한하며 초과 요청은 429 Too Many Requests로 거부한다. 현재 인메모리 방식이라 다중 인스턴스에서는 공유 제한기가 필요하다.

한계 1JSON 안에 @class 패키지 경로가 함께 저장됨 → MSA 전환 시 다른 서비스에서 역직렬화하면 ClassCastException 위험.

한계 2Cache Stampede 미대응 — Redis 장애나 동시 만료가 발생하면 요청이 Postgres로 집중될 수 있다.

확장 시 검토(1) 명시적 DTO serializer로 서비스 간 계약 분리. (2) Bulkhead·요청 병합·TTL jitter로 fallback 집중 완화. (3) 가용성 요구와 복구 목표가 단일 인스턴스 범위를 넘을 때 Sentinel 또는 Cluster 검토.

현 사이트가 안 가는 이유(1)(2)는 별도 Unit의 개선 비교 회고로 분리할 예정이다. (3) Cluster는 여러 노드 운영에 필요한 메모리 때문에 현재 t4g.small 환경에 적합하지 않다.

첫 캐시 실행은 미스라 DB로 떨어집니다(첫 막대만 길어요). 두 번째부터 전부 히트. 벤치마크는 연결 peer 기준 분당 누적 400회로 제한됩니다. "캐시 비우기"로 다시 콜드 상태에서 시작할 수 있습니다.

아키텍처 결정 — Redis를 어디에, 어떤 자료구조로 쓰는가

  • 역할: Redis는 원본 저장소가 아니라 반복 비용이 큰 조회 결과를 가속하는 계층이다. Postgres를 Source of Truth로 유지하고, 캐시 미스 시 DB 조회 후 채우는 Cache-Aside 패턴을 선택했다.
  • 현재 자료구조 — String(Key-Value): category-stats::<카테고리>를 키로, 집계 DTO 전체를 JSON 값으로 저장한다. 한 키로 결과 전체를 함께 읽고 만료시키는 조회 모델이므로 부분 필드 갱신용 Hash보다 단순하고 원자적인 구조가 맞다.
  • 다른 자료구조의 선택 기준: 객체 일부를 자주 갱신하면 Hash, 중복 없는 소속·권한 판별이면 Set, 점수 기반 순위·시간순 조회면 Sorted Set, 소비자 그룹이 필요한 이벤트 처리면 Stream을 검토한다. 자료구조는 기술 선호가 아니라 접근 패턴으로 결정한다.
  • 키·TTL: 도메인과 조회 조건이 드러나는 네임스페이스 키를 사용하고 TTL 60초로 성능과 신선도의 경계를 정했다. 실제 업무에서는 환율·마스터 데이터처럼 변경 주기와 stale 허용 시간에 따라 TTL을 다르게 둔다.
  • 현재 무효화 범위: 이 데모에는 상품 쓰기 API가 없다. 화면의 “캐시 비우기”는 비교 실험을 다시 시작하기 위한 수동 @CacheEvict(allEntries = true)이며, DB 저장 이후의 선택적 무효화를 구현한 것으로 설명하지 않는다.
  • 업무 쓰기 추가 시: DB transaction commit 이후 변경된 category key만 삭제하는 방식을 우선 검토한다. DB rollback인데 캐시만 먼저 지워지는 순서와, 삭제 실패로 stale 값이 남는 경우를 통합 테스트해야 한다.
  • 장애 경계: cache get·put 실패는 DB 조회 결과를 반환하도록 fail-open 처리한다. 반면 evict·clear 실패는 stale 데이터를 정상처럼 제공할 수 있으므로 예외를 호출자에게 전달한다. 대규모 트래픽에서는 Bulkhead·TTL jitter·요청 병합으로 fallback 집중도 함께 제한해야 한다.

이 데모가 실제로 무엇을 측정하나요?

  • SELECT sub_category, count, avg(price), min, max FROM product WHERE category = ? GROUP BY sub_category — Postgres 16에서 인덱스 없이 풀스캔.
  • 응답 시간(ns) → ms 변환 후 통계: 평균·최소·최대.
  • 캐시 키: category-stats::<카테고리명> · TTL 60s · 직렬화 GenericJackson2JsonRedisSerializer.
  • Redis GET 실패 시 CacheErrorHandler가 조회 오류를 격리하고 @Cacheable 대상 메서드가 DB를 조회한다. PUT 실패도 DB 결과는 반환하지만 캐시는 채워지지 않는다.
  • 수동 clear 실패는 성공 응답으로 숨기지 않고 오류로 반환한다.
