## 01 — SSH 키 머신 SID (`01-ssh-key-machine-sid`)

### 추가 메모

OneDrive·기업 보안 정책 폴더 안의 `.ssh/` 는 권한 변경이 자동 되돌려질 수 있음. **`C:\sshkeys` 같은 `%USERPROFILE%` 밖 경로** 사용이 안전.

### 면접 답변용

> *"Windows 에서 컴퓨터명과 사용자명이 같으면(흔한 케이스) icacls 가 사용자가 아니라 머신 SID 에 권한을 grant 하는 경우가 있어요. 그래서 사용자가 자기 파일을 읽지 못하는 역설적 상황이 생기는데, 디버깅의 핵심은 SID 의 RID 부분(끝에 `-1001` 같은 숫자)이 있는지 확인하는 겁니다. 이름 해석 우회로 `icacls /grant:r *<SID>:F` 패턴이 가장 확실합니다."*

## 02 — Cloudflare SSL Full 521 (`02-cloudflare-ssl-full-521`)

### 면접 답변용

> *"Cloudflare 521 은 origin 중단뿐 아니라 SSL 모드와 origin 프로토콜 불일치로도 발생합니다. 당시 origin 은 HTTP만 제공하는데 Full 모드가 HTTPS 연결을 시도해 실패했습니다. Flexible 전환으로 가용성을 임시 복구했지만, 장기 조치는 origin 인증서 구성과 Full(strict) 전환, 그리고 프록시 경로만 허용하는 접근 제한입니다."*

## 03 — Postgres 포트 충돌 (`03-postgres-port-conflict`)

### 면접 답변용

> *"로컬에서 'auth failed' 보이면 자격증명부터 의심하는 게 본능인데, 사실 가장 많이 막히는 건 포트 충돌입니다. 한 머신에서 여러 프로젝트를 돌리면 같은 표준 포트를 쓰는 컨테이너가 흔하거든요. 디버깅 핵심은 *"호스트와 컨테이너 안에서 같은 명령으로 인증 결과가 다른지"* 확인하는 거고, 다르면 99% 다른 서비스에 닿고 있는 겁니다. 그래서 docker-compose 의 호스트 포트는 표준 포트 - 1 또는 +1 로 미리 분리하는 게 운영 안전 습관입니다."*

## 04 — Cloudflare SSL 모드 결정 (`04-cloudflare-ssl-mode-decision`)

### 면접 답변용

> *"초기에는 인증서가 없는 origin을 빠르게 복구하려고 Flexible을 사용했지만, OAuth와 관리자 기능이 추가되면서 전제가 바뀌었습니다. 그래서 장애 복구 선택과 최종 보안 상태를 분리했고, origin 인증서와 Full(strict), origin 직접 접근 차단을 운영 목표로 정했습니다. 아키텍처 결정은 기능이 늘 때 다시 위협 모델을 검토해야 한다고 배웠습니다."*

## 06 — Elastic IP 2024 과금 (`06-elastic-ip-2024-pricing`)

### 면접 답변용

> *"EC2 의 public IP 는 stop/start 시 바뀌어서, DNS 가 옛 IP 가리키면 즉시 다운입니다. 처음엔 Elastic IP 가격이 부담될까 봐 안 붙였다가 정확히 그 함정에 빠졌어요. 그런데 알고 보니 2024 년 2 월부터 AWS 가 모든 public IPv4 를 시간당 $0.005 로 과금하기 시작해서 — EIP attach 든 일반 IP 든 비용이 같습니다. *공짜 IPv4 시대가 끝난* 거고, 이제 EIP 안 쓸 이유가 없어요. 월 ~$3.6 의 운영 안전망 비용을 받아들이는 게 정답입니다. 그리고 인스턴스 terminate 시 EIP 도 같이 release 안 하면 조용히 계속 청구되는 함정도 있어서, 정리 명령을 종료 절차의 마지막 단계로 박아두는 게 운영 위생입니다."*

## 08 — 외부 리뷰 피벗 (`08-third-party-review-pivot`)

### 면접 답변용

> *"이 사이트의 Kafka 데모를 외부 LLM 에 던져서 평가받았더니 — FixedBackOff 의 블로킹 재시도가 throughput 그래프와 모순된다는 정확한 지적을 받았어요. 처음엔 *'어떻게 반박할까'* 생각했는데, 그 자체가 주니어 패턴이라는 걸 깨달았습니다. 그래서 데모 페이지 상단에 *trade-off 박스* 를 박아서 — 현재 구현, 한계, 엔터프라이즈급으로 가려면 어디로 가야 하는지, 그리고 *왜 이 인스턴스에선 안 가는지* 까지 사이트가 먼저 말하게 했어요. 결과적으로 *시연 가능한 라이브 데모* 보다 *의사결정과 trade-off 의 노출* 이 이 사이트의 진짜 메시지가 됐습니다. 시니어 톤이 만들어지는 과정이라고 봐요."*

## 09 — Kafka ADVERTISED_LISTENERS 함정 (`09-kafka-advertised-listener-trap`)

### 면접 답변용

> *"Kafka 환경 셋업의 1 등급 함정이 ADVERTISED_LISTENERS 입니다. LISTENERS 는 broker 가 *실제로 bind* 하는 주소이고, ADVERTISED_LISTENERS 는 broker 가 metadata 응답으로 client 에게 *알려주는* 주소 — 이름이 비슷한데 역할이 완전히 다릅니다. 이게 잘못되면 첫 bootstrap 연결은 성공하고, 그 다음 metadata 받은 후부터 잘못된 주소로 무한 retry. 디버깅 신호는 *Spring 설정과 WARN 메시지의 주소가 다르면 broker 가 광고한 주소* 라는 비대칭이고요. Docker compose 네트워크 안에선 서비스 이름이 hostname 으로 resolve 되니까 `kafka:9092` 가 정답이고, `localhost:9092` 는 *client 컨테이너 자기 자신* 을 가리켜서 절대 안 됩니다."*

이 함정은 *Confluent 공식 문서* 와 *Apache Kafka FAQ* 에 단골로 나오는 항목이지만, *"비슷한 이름의 두 변수가 완전히 다른 역할"* 이라는 인지 부담 때문에 처음 만나면 디버깅에 1~2 시간 쓰는 게 흔합니다.
