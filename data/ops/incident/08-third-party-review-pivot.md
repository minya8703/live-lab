## 배경

이 사이트의 Kafka 데모와 Redis 데모를 다른 LLM 에 던지고 *"이 데모가 시나리오 목적에 맞게 설계됐는지 기술적으로 평가"* 를 요청. 받은 평가가 정확하고 단호했다 — 부인이 불가능한 종류의 비판.

## 평가 받은 내용 (요약)

### Kafka 데모

> *"Spring Kafka 의 예외 처리 기본 메커니즘 (기능적 검증) 으로는 90 점, 실제 고성능 SaaS 의 대용량 트래픽 처리 (비기능적 운영 패턴 증명) 로는 50 점."*

핵심 지적:
1. **FixedBackOff 블로킹 모순** — `DefaultErrorHandler` + `FixedBackOff(500ms × 3)` 은 레코드 단위 블로킹. 17 의 배수 메시지가 걸리면 해당 파티션 컨슈머 스레드가 1.5초 stall → throughput 그래프가 계단식으로 낙하. *"라이브 증명"* 의 메시지 자체와 모순.
2. **3 파티션 비대칭** — 한 파티션이 stall 동안 다른 둘은 오프셋 폭주 → 성공 카운트 spike + DLT 점진 증가의 비대칭. Straggler 문제.
3. **500ms 풀링 한계** — Kafka 의 ms 단위 처리를 500ms 단위로 가져오면 *재시도 중인지 완료인지* 시각적 매칭 어려움.

개선 방향 (평가자 제시): **Non-blocking Retry Topic 패턴** — 메인 토픽을 막지 않고 `order.retry.500ms` → `order.retry.5s` → `order.DLT` 단계 분리.

### Redis 데모

> *"A+ 등급의 페이지 — 장애 전파 방지 (Fault Isolation) 마인드셋 완벽."*

마이너 지적:
1. **`@class` 직렬화 함정** — `GenericJackson2JsonRedisSerializer` 가 JSON 안에 패키지 경로 저장. MSA 전환 시 다른 서비스 패키지 구조 다르면 `ClassCastException`.
2. **Cache Stampede 누락** — Redis 진짜 다운 시 수천 동시 요청이 DB 한 번에 → DB CPU 100% 도미노. Resilience4j Circuit Breaker 미적용.

개선 방향: `Jackson2JsonRedisSerializer<DTO>` + Circuit Breaker + Bulkhead.

## 결정 — 부인하지 않고 정직 모드 전환

세 가지 선택지가 있었다:

| 옵션 | 결과 |
|---|---|
| A. 비판 무시 / 무대응 | 사이트의 *"라이브 증명"* 주장이 자기 모순으로 남음. 시니어 면접관에게 같은 비판 받을 가능성 100% |
| B. 비판받은 패턴 즉시 코드 변경 | 사이트 전체 재구현. 2~3 주 소요. 그리고 *방향 명시* 가 *완성된 데모* 보다 어떻게 더 강한지 증명 못 함 |
| **C. 비판을 자기 진단으로 흡수 + 사이트 톤 전환** | **선택** — 사이트 정체성을 *"live 증명" → "trade-off 인지 + 다음 방향"* 으로 재포지셔닝 |

C 의 논리: **주니어 = "내 코드 완벽" → 비판받으면 무너짐. 시니어 = "이 코드의 한계는 X, 다음 방향은 Y" → 비판이 자기 진단과 일치하면 신뢰 시그널.**

## 적용한 변경

### 1. 모든 라이브 페이지 상단에 통일 `trade-off` 박스

`/lab/kafka.html`, `/lab/redis.html`, `/lab/chat.html` 에 노란 박스 추가:

```
⚖ 이 데모의 trade-off (의식적 선택)
  현재 — [실제 구현]
  한계 — [평가자가 짚은 정확히 그것을 솔직히 인정]
  엔터프라이즈급 — [어디로 가야 하는가, 구체 클래스/패턴/라이브러리 명시]
  현 사이트가 안 가는 이유 — [이 인스턴스의 메모리·시간 제약]
```

평가자가 짚은 내용을 *그대로* 박스 안에 박았다. *"이 데모는 X 라는 한계가 있다"* 를 사이트가 먼저 말한다.

### 2. 랜딩 카피 변경

```
Before: "Kafka · Redis · MSA를 실제로 돌려보고, AI-DLC로 만들어가는 백엔드 진열대."
After:  "Kafka · Redis · MSA 를 t4g.small 2GB 안에서 다루고,
        그 환경의 trade-off 와 다음 방향까지 가감없이 노출합니다."
```

`section-sub` 도 *"이력서의 숫자가 사실인지"* → *"의사결정의 노출이 메시지"* 로.

## 일반화한 룰

> **사이트가 자기 약점을 먼저 말하면, 외부 평가자가 그걸 *공격* 으로 못 쓴다.**

세 가지 운영 원칙:

1. **라이브 데모의 한계는 페이지 안에 박는다** — 별도 회고/주석이 아닌 *데모 페이지 그 자체* 에. 사용자가 데모를 보는 순간 trade-off 박스가 같이 보임.
2. **"엔터프라이즈급으로 가려면" 항목은 구체적이어야** — "더 잘 하려면" 같은 추상 표현 금지. *클래스명 · 라이브러리 · 패턴* 까지 명시. (예: `@RetryableTopic`, `Resilience4j Circuit Breaker + Bulkhead`)
3. **"안 가는 이유" 도 솔직히 명시** — 모르는 것이 아니라 *지금 인스턴스가 무리* 라는 사실 자체가 기술적 의사결정의 시그널이 됨.

## 메타 — 이 회고 자체의 가치

이 사이트는 *"AI-DLC 일지 페이지"* 와 *"운영 회고 페이지"* 라는 두 메타 인지 콘텐츠를 이미 갖고 있었다. 이번 회고는 **세 번째 층 — *"외부 평가에 사이트가 어떻게 반응하는가"* 의 메타 인지**. 

면접관이 *"이 데모 어디가 약해요?"* 라고 물으면 — 사이트가 이미 답을 갖고 있다. *"여기 박스 안에 적어뒀습니다"*. 질문이 자기 진단의 확인이 된다.

## 면접 답변용

> *"이 사이트의 Kafka 데모를 외부 LLM 에 던져서 평가받았더니 — FixedBackOff 의 블로킹 재시도가 throughput 그래프와 모순된다는 정확한 지적을 받았어요. 처음엔 *'어떻게 반박할까'* 생각했는데, 그 자체가 주니어 패턴이라는 걸 깨달았습니다. 그래서 데모 페이지 상단에 *trade-off 박스* 를 박아서 — 현재 구현, 한계, 엔터프라이즈급으로 가려면 어디로 가야 하는지, 그리고 *왜 이 인스턴스에선 안 가는지* 까지 사이트가 먼저 말하게 했어요. 결과적으로 *시연 가능한 라이브 데모* 보다 *의사결정과 trade-off 의 노출* 이 이 사이트의 진짜 메시지가 됐습니다. 시니어 톤이 만들어지는 과정이라고 봐요."*
